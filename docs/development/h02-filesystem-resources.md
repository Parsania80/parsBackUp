# H02 protected filesystem and native resource contract

Recorded before implementation on 2026-11-15. This increment hardens currently enabled **writable versioned fixture** store operations. It preserves pending key-bootstrap work, legacy constructors, existing artifact/key/plan bytes and the store's activity/job/artifact lock identity. Production remains disabled; true snapshot storage, bounded catalogue scanning, structured native-job failure receipts and service/cgroup containment remain separate H02 gates. This is a declarative contract, not a flow.

## Store filesystem boundary

Versioned native create may create the final store directory at mode 0700 inside an existing protected parent; other versioned store commands require the store to exist. No recursive parent creation or automatic chmod is performed. Every ancestor is opened relative to a validated directory descriptor with no-follow/nonblocking flags, root/service ownership and no group/other write. The store and existing top-level `artifacts`, `staging`, `scratch`, `plans`, `locks` directories must be real directories owned by the service UID, mode 0700 or stricter. Existing inventory files/sidecars must be service-owned regular no-follow single-link files with mode 0600 or stricter. Unsafe existing state refuses before migration/recovery/native effects. A rebuild crash after linking the previous index can leave the current index with two links; versioned commands deliberately refuse that state for inspection rather than guessing which alias to unlink. Internal layout creation remains explicit for native store opening/recovery; key/status/config/profile and dry-run operations do not open a store.

A held root descriptor anchors subsequent backend path resolution through the owning process's procfs descriptor path. The same physical `locks/activity.lock`, scope and artifact claim files are used; no second lock domain is introduced. The root descriptor remains alive through store/stage/view/artifact-use lifetimes and native child file access. Renaming/replacing the configured root after validation cannot redirect an active operation. Native subprocesses run under the same service UID/namespace and may resolve their parent's protected descriptor; Linux procfs is required. User-facing recovery paths and saved previous-inventory receipts are mapped back to the configured root. SQLite’s ordinary paths retain its full no-follow flag. For an exact live directory descriptor of the current process, the adapter separately opens the final database with no-follow/nonblocking flags before allowing SQLite to resolve the trusted procfs ancestor. SQLite retains its own database/journal descriptors and pathname behavior; moving a root after a SQLite connection opens is not a transaction-continuity guarantee. Same-UID namespace mutation remains outside this boundary. New inventory files are explicitly created at 0600 without changing the process umask or repairing existing modes. Root/service administrators remain trusted; hostile same-UID mutation, mounts and source-selected SQL are not sandboxed by this mechanism. Descendant layout is private, not recursively scanned at every open. Unsupported/malicious per-artifact entries continue to refuse under existing bounded/fixed-file readers.

Actual key directories used by native operations must not be inside the opened store, including inode aliases; lexical disjointness alone is insufficient. Restore does not probe writer-only keys. This increment does not re-open offline-command passfiles or implement arbitrary bind-mount isolation. Snapshot/external scratch separation will be checked by that increment before enabling it.

## Versioned resources

Optional closed `[resources]` has the following deployment limits; omitted fields use these defaults. Unknown fields/zero/overflow/out-of-range values refuse structurally, before opening resources. These fields do not enable production or alter fingerprints/plan bytes. Execution uses the current validated limits; reducing limits may refuse an otherwise valid saved plan/artifact.

| Field | Default | Accepted range | Enforcement |
|---|---:|---:|---|
| `max_payload_bytes` | 64 GiB | 1–64 GiB | Plaintext accepted from pg_dump and payload decryption |
| `max_globals_bytes` | 8 MiB | 1–8 MiB | Globals export and globals decryption |
| `max_stage_bytes` | 65 GiB + 16 MiB | 1–default | Combined bytes written into one new artifact stage, including encrypted metadata/signature/public record |
| `max_scratch_bytes` | 64 GiB + 16 MiB | 1–default | Aggregate plaintext held by live scratch views within one store handle |
| `min_free_bytes` | 64 MiB | 1 MiB–1 TiB | Available bytes observed on the destination filesystem before each guarded data write |

Manifest plaintext remains capped at 64 KiB. Per-file ciphertext inspection bounds are plaintext limit + one 16-byte age tag per 64-KiB chunk (including final chunk) + 64 KiB header allowance. Native store payload/globals/manifest hashing is bounded before and during reads, rather than trusting a mutable metadata length. Legacy APIs retain their existing limits and behavior. No new environment/native-option override is introduced.

Before any guarded write, the whole incoming buffer must fit its plaintext/file and shared stage/scratch budgets, and observed `f_bavail * f_frsize` must cover the buffer plus reserve. No over-limit byte is written. Accounting uses checked arithmetic and releases scratch charges only when the owned view is removed; overlapping views share one handle's quota. Short writes/refusals maintain exact charges. This is an observed reserve, **not** a filesystem reservation or quota against other processes; concurrent unrelated writes, metadata/SQLite/journal growth and PostgreSQL target-database growth can still consume disk. Staging limits apply to artifact data/metadata, not SQL inventory size. Database effects already started remain for operator inspection under existing semantics; no fabricated zero-side-effect report.

Existing native stdout/stderr capture remains 64 KiB per stream, with overflow drained/refused, and native streaming uses the guarded consumer. Existing per-subprocess timeout is 1–3600 seconds from configuration, with process-group deadline/exit cleanup. There is no new whole-job timeout, cancellation caller, process-tree sandbox or cgroup guarantee in this increment. Decrypted views/stages are cleaned on ordinary failure/drop; crash leftovers retain existing maintenance recovery ownership. Snapshot reads remain blocked before any writable lock/scratch path.

## Errors and verification

New safe generated codes: `FILESYSTEM_UNSAFE`, `RESOURCE_LIMIT`, `DISK_RESERVE_LOW`. Partial database effects continue to use existing safe native-operation/job semantics. Resource failures must stop publication/cleanup temporary views; configured low limits are not retried or bypassed. No diagnostics include SQL, plaintext/key contents or raw native stderr.

Acceptance requires protected/foreign/mode/symlink/FIFO paths, key/store alias checks, descriptor root replacement and child access, identical physical activity-lock contention, checked byte/reserve accounting, simultaneous scratch-view quota/release, exact-limit/overflow refusal and no publication/leaked plaintext on bounded failures. Actual PG16/17/18 create and source-loss portable/full DR restore must pass with small-limit/refusal controls; prior legacy/key/signing regressions and frozen vectors remain required. Full H02/production acceptance is not implied.
