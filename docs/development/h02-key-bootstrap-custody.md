# H02 validated key bootstrap and custody contract

Recorded before implementation on 2026-11-15. This increment applies to **versioned fixture** configuration; production continues to refuse every operation except structural checking. Legacy lifecycle commands and formats retain their existing behavior, including their documented limitations. The existing lifecycle operating document is unchanged. This is a declarative contract, not a flow.

## Custody and resources

| Operation | Key resources | Other resources |
|---|---|---|
| Writer `key generate` | All four destinations must be absent; generate one encryption and one signing pair | Existing protected parent directories only; no source/tools/store/scratch |
| Writer `key publish` | Identity and signing seed required; derive missing public halves; existing public halves must match and are never replaced | Same protected parents; no source/tools/store/scratch |
| `key status` | Writer: all four, checking pairs; reader: identity + verifier only; public: verifier only; inventory: none | No store/source/tools/scratch; permitted with read-only config |
| Real signed backup create | All four, protected and pair-matched before store access | Existing native requirements unchanged |
| Restore plan/run | Identity + verifier only, including when writer config invokes restore | No recipient or signing-secret access; existing native/store requirements unchanged |
| Profile validation / create dry-run / keyless inventory | No key access | Existing boundaries unchanged |

Permitted authenticated offline backup reads remain gated for a later increment; this work does not add snapshot storage support. Status reads are independent of store existence. Status proves pair agreement only where both halves are in custody; a reader's identity and verifier belong to different cryptographic families and have no mathematical pair relationship. Configuration role is not an OS access-control boundary.

## Descriptor and publication boundary

Every key parent already exists: this versioned increment never creates directories. Absolute normalized paths, no symlinks at any component, root/service-owned ancestry without group/other write, and descriptor-relative opens are mandatory. Secret final files are regular service-owned files with mode 0600 or stricter (no execute/special/group/other bits); public files are regular root/service-owned with no execute/special/group/other-write bits. Reads are bounded by the existing crypto key-file limit, validate the same suite/hex grammar, and parse the inspected descriptor without reopening its pathname. Configured key files cannot alias by device/inode; identical normalized paths already refuse structurally. Key commands never probe a configured passfile; the native authentication boundary retains its own passfile/key alias checks for the operation’s actual custody. Broader store/scratch filesystem identity and service-hardening gates remain separate H02 work.

Unique parent-directory descriptors are locked in sorted device/inode order with nonblocking shared locks for custody reads/status and exclusive locks for mutations. These advisory directory locks create no files and are shared by versioned key operations; they do not replace artifact/store activity locks. Occupancy is checked under those locks, treating dangling symlinks and special files as occupied. Generate validates **all four** destinations before entropy generation or publication. Publish validates both secret seeds and all existing public halves/destinations before writing any missing public half. A missing/invalid later signing input cannot leave a new recipient behind. Cooperating concurrent bootstrap operations serialize or refuse `KEY_BUSY`.

All new files are fully written, assigned exact modes (0600 secrets, 0644 public), synced and parsed/read back in anonymous `O_TMPFILE` staging in their destination directories before any final name is linked. Linux `/proc/self/fd` and filesystem support for anonymous staging are required; unavailable support refuses before final publication. Existing crypto formats/suites/IDs and parser semantics do not change. Published links use no-replace descriptor-relative `linkat`; destination directories are synced after each link. Generate order is identity, signing seed, recipient, verifier; publish writes missing recipient then missing verifier. No existing file is overwritten, removed or automatically repaired. Staged anonymous files disappear on drop/crash unless already linked. This is **not** a multi-file atomic transaction.

Preflight or anonymous staging failure returns a safe error with null data and no final publication. A handled publication failure before the first final link has empty `created` and all intended roles `pending`; after any link it returns `KEY_PARTIAL`, status `partial`, exit 1 and the exact `created` prefix/remaining `pending` roles. `durability_confirmed` is false if a linked directory could not be synced. No automatic secret rollback/retry or overwrite is attempted. Abrupt process death may emit no receipt; surviving final names are retained, `generate` refuses any occupied destination, and `publish` can complete missing public halves when both surviving seeds are valid. A crash leaving only one seed requires explicit operator custody inspection/recovery; no new seed is silently generated beside it. Matching public halves make publish idempotent, but cannot bootstrap independent trust by themselves.

## Reports and verification

Versioned status data is exactly `{keys:[...]}`. Each public fact has `path`, `role` (`identity`, `recipient`, `signing`, `verifying`), `suite`, four-digit octal `mode`, and 16-character public `fingerprint` (recipient ID for encryption files, signer ID for signing files). No seed or full private encoding is returned. Mutation data additionally has `created`, `pending`, `durability_confirmed`; `keys` contains complete validated facts on success and an empty array on handled publication failure. Legacy JSON mappings remain unchanged. Codes are generated safe text: `KEY_UNSAFE`, `KEY_INVALID`, `KEY_OCCUPIED`, `KEY_BUSY`, `KEY_OPERATION_FAILED`, `KEY_PARTIAL`.

Acceptance covers role/read-only/production matrices, missing/unsafe later inputs before writes, pair mismatch, aliased/link/FIFO/oversized/permission inputs, anonymous staged read-back, no-overwrite/idempotent public recovery, deterministic handled publication failures, concurrent directory ownership and killed bootstrap recovery. A new-key native PG16/17/18 signed backup and reader-only portable/full DR source-loss restore must pass. Legacy workspace/key lifecycle regressions and frozen vectors remain required. Full H02/V acceptance, production release and T03 remain open.

The local adapter reuses the already locked workspace `zeroize` dependency to wipe temporary secret encodings used by anonymous staging; no new package/version is introduced. The crypto descriptor loaders share the existing suite/length parser; legacy key loading paths remain compatible.

Accepted verification (2026-11-15): 293 workspace tests, strict locked/offline Clippy and formatting; the actual process fault/crash drill including four SIGKILL boundaries; and PG16/17/18 new-key native recovery, legacy key lifecycle and signed-artifact matrices (nine script/major combinations). All 91 frozen inputs match; the [roadmap evidence](../../project.md#44-h02-validated-key-bootstrap-and-custody--2026-11-15) records exact scope and limits. This accepts the increment, not full H02 or production use.
