# M5a inventory and job read contract

A01 adds `job list`, `job inspect JOB_UUID`, and `inventory check` using the configured storage root. These commands open the existing inventory read-only: they do not create directories or databases, migrate a schema, sweep jobs, load keys, or contact PostgreSQL. Job reads first run SQLite's structural integrity check, so a damaged index is not reported as an absent job; job fingerprints must be valid and match the bound source. Before reporting a missing job, inspection also validates the other job rows. The binding is read from the inventory itself; it is not authenticated by this operation. A copied inventory can therefore be inspected without the source server or keys. Schema v1 has no job table: job reads fail rather than migrate it. The inventory is an index, not proof that an artifact exists or is trustworthy.

## JSON and ordering

`--output json job list` returns `{"jobs":[...],"audit_recorded":false}` in ascending `started_at_utc`, then ascending `job_id` order. `job inspect` returns `{"job":{...},"audit_recorded":false}`. Each job has `job_id`, `backup_id` (UUID or `null`), `source_fingerprint`, nullable `profile_fingerprint`, `state` (`running`, `staged`, `complete`, `failed`, or `interrupted`), `started_at_utc`, `updated_at_utc`, nullable `operation`, and nullable `target_fingerprint`. Schema v5 records `backup` or `restore` for new jobs. Older rows retain `operation: null`; it must not be guessed from an artifact or event. Restore rows report their artifact ID and target fingerprint, with profile unknown. For example, an older job can be:

```json
{"jobs":[{"job_id":"00000000-0000-4000-8000-000000000001","backup_id":null,"source_fingerprint":"0123456789abcdef","profile_fingerprint":"0123456789abcdef","state":"running","started_at_utc":"2026-01-01T00:00:00Z","updated_at_utc":"2026-01-01T00:00:00Z","operation":null,"target_fingerprint":null}],"audit_recorded":false}
```

`inventory check` runs SQLite `integrity_check` and returns `{"valid":true,"schema_version":5,"source_fingerprint":"0123456789abcdef","problems":[],"audit_recorded":false}` when clean. If SQLite reports structural problems, `valid` is false, `problems` contains its diagnostics, and the command exits 1 after printing the report. A clean structural check does not authenticate rows, artifacts, or their estate provenance. These read commands do not write audit events.

## Errors and exit codes

Successful commands exit 0. Inventory-related failures exit 1, use the existing stderr `error:` cause-chain format, and include one stable category: `INVENTORY_OPEN_FAILED` for missing, inaccessible, invalid or unsupported inventory; `INVENTORY_READ_FAILED` for a failed job query or integrity check; and `JOB_NOT_FOUND` when a valid inventory has no requested job. Structural problems found by a completed check exit 1 with `INVENTORY_CORRUPT`. Configuration errors retain the existing error format; invalid CLI arguments, including malformed UUIDs, remain Clap errors with exit 2. Failures do not create or modify the inventory. Schema v1 can be structurally checked but cannot supply jobs without a separately authorized writable migration.

## A02 discovery and reconciliation contract

`inventory list` observes all three shapes using an existing, bound inventory and makes no changes; it takes no activity claim, so a concurrent publication may be observed as incomplete. `inventory reconcile` is an explicit writable operation on an existing, bound current-schema inventory. It never adopts unregistered artifacts, deletes files, guesses private facts, verifies origin or upgrades trust. It takes the store's exclusive activity claim without waiting; a busy store fails with `RECONCILE_BUSY` before scanning or changing rows. A complete directory scan and inventory integrity check are required before any update; an I/O error aborts the entire operation and never implies a missing artifact. Invalid entries are reported individually with bounded reason codes, not arbitrary file contents.

The JSON result is `{"entries":[...],"audit_recorded":true}`; `audit_recorded` is true only if a state-change event was written. Entries have `backup_id` (UUID or null for an invalid name), `shape` (`v1-signed`, `age-unsigned`, `plaintext-dev`, or null), `status` (`registered`, `unregistered`, `missing`, `incomplete`, `conflict`, or `invalid`), `reason` (a bounded code or null), and `provenance` (`unconfirmed` or null). Results sort by UUID, with invalid names last. Observation reports file presence and consistency with recorded facts, not signature verification. An invalid or incomplete registered entry is conflict; an entry not present on disk is missing; other unregistered entries remain unregistered. Mixed or ambiguous shapes, malformed components and mismatch against an existing row are conflicts. Any component symlink is refused without following it. Unknown names are invalid and never supplied as paths by the user.

The scanner uses Linux `/proc/self/fd` to enumerate already-open directory descriptors; if procfs is unavailable, it fails without changing inventory state. This is a platform limitation for future non-Linux support.

For registered rows only, reconciliation updates `state` to `missing`, `conflict`, or `registered` when the observation changes; the state update and its safe audit event are one SQLite transaction. No row or other field is replaced, so private profile/completion facts survive. Repeating an unchanged reconciliation adds no event. For signed rows, recorded sizes and digests detect changes to the payload or encrypted manifest; this does not authenticate the signature or globals, or establish source or archive validity. Development rows have no previously recorded payload digest, so a consistently replaced manifest and payload may go undetected. Missing inventory, malformed inventory, incomplete scan or lock failure exit 1 without changing rows. Future lifecycle fields must remain untouched by these updates.

`inventory list` is the mixed-shape discovery command; the older `backup list` retains its shape-specific behavior. The activity claim coordinates cooperating operations, not arbitrary external modifications to the filesystem during a scan.

The new state and audit words use the existing unconstrained schema-v2 text columns. An older build that does not know these words will refuse to read affected artifact or audit rows; do not treat that refusal as data loss or silently downgrade the values.

## A03 adoption and rebuild

`inventory rebuild --source-fingerprint FINGERPRINT --dry-run` scans artifact files without opening the inventory or loading keys, so it also works when the index is missing or corrupt. The fingerprint must be 16 lowercase hexadecimal characters. Preview makes no changes, does not validate an existing inventory binding, and reports observed candidates as `unregistered` because it intentionally does not read that index. The report uses the same entries as A02 and adds `source_fingerprint`, `estate_provenance: "unconfirmed"`, `unknown_facts`, `lost_history`, and `audit_recorded: false`. A complete scan is required; incomplete, invalid and conflicting entries remain visible and are not authenticated.

The fingerprint is an operator-supplied expectation, not proof of an artifact's origin. A rebuilt index cannot recover job, audit, protection or verification history, and cannot infer private profile or completion facts. A dry run does not authorize a later replacement.

`inventory adopt ID --source-fingerprint FINGERPRINT` requires an existing inventory bound to that fingerprint and an unregistered, complete, consistent artifact. It records only bounded public facts, leaves profile and completion unknown, persists unconfirmed provenance, and adds an adoption event in the same transaction. Already registered, malformed, foreign-bound, and busy cases are refused. An older supported schema is upgraded to the current version when adoption is explicitly requested; older builds refuse newer schemas.

For replacement, first run `inventory rebuild --source-fingerprint FINGERPRINT --prepare-rebuild`, inspect the entries and the reported losses, and retain its `plan_id`. Then run `inventory rebuild --source-fingerprint FINGERPRINT --confirm-rebuild --plan-id PLAN_UUID`. Preparation writes a private plan under the store root. The plan binds the expected source and a digest of all observed artifact files and the old inventory. Confirmation loads it under the exclusive activity claim and refuses stale plans, invalid or incomplete entries, a readable foreign estate, newer schema, symlinked inventory, or SQLite sidecars. It builds a private new database, records provisional rows and a rebuild event, validates and syncs it, links any old inventory under the returned `previous_inventory` path, syncs the directory, then atomically replaces the index and syncs again. The old database can be opened at that path for recovery. If the old database is corrupt its estate cannot be established; it is preserved, and all newly indexed provenance remains unconfirmed.

Schema v3 records provisional provenance independently of lifecycle state. Reconciliation never upgrades it. Once a signed manifest has been authenticated and decrypted, its source must match the provisional inventory estate or the read fails; matching does not itself clear the provisional marker. If an inventory exists but cannot be read, authenticated signed reads fail closed until the inventory is recovered or rebuilt; a missing inventory remains compatible with signed reads. Signature-only verification cannot establish source provenance. Activity claims now span the entire backup job, including before staging and after publication, so replacement cannot race job transitions. Plans and old inventories are retained for operator cleanup; they are not adversarial rollback protection. A crash after the replacement but before directory sync may leave an uncertain result; inspect the active and previous inventories before retrying. Filesystem changes by non-cooperating processes remain outside the activity-lock guarantee.

## A04 verification and enrichment contract

Verification events distinguish `signature`, `checksum`, and `archive`, and record success or failure, UTC time and artifact ID. A successful signed observation is bound to the observed payload and encrypted-manifest SHA-256 digests; a failure may have unknown digests when verification could not establish them. Events contain no arbitrary diagnostic text. Enrichment may use profile fingerprint and completion time only from a signed, authenticated manifest whose source and ciphertext digests match the registered row. It must not overwrite conflicting known facts or promote an unregistered artifact. The event and enrichment must commit atomically, and changed bytes must never inherit an earlier successful observation. Read-only verification must report that no event was recorded.

`backup verify ID --level signature|checksum|archive` records an observation for an existing registered inventory row. It does not create an inventory or adopt unregistered artifacts; successful output contains `audit_recorded`, which is false when no row exists. An existing writable index is migrated to schema v4 if needed. Use `backup verify ID --level LEVEL --read-only` to skip both migration and observation writes; its output says `audit_recorded: false`, including in the failure diagnostic. If recording fails after successful verification, the command fails and explains that verification succeeded but the observation could not be recorded. Failure diagnostics are not saved in SQLite.

`--read-only` controls inventory recording; existing store initialization, activity locks and decrypted scratch can still require writable storage. True verification on a read-only mount remains an H02 requirement.

`inventory verification ID` reads the ordered event history without writing. JSON contains `events` and `audit_recorded: false`; each event has `backup_id`, `at_utc`, `level`, `outcome`, nullable `payload_sha256` and `manifest_sha256`, and `current`. A later verification failure or a reconciliation that marks the row missing or conflicting invalidates earlier observations in the same transaction. Returning the row to registered does not revive them. `current` reflects the last persisted observations, not a fresh scan: a file can change after the event and before another verification or reconciliation. Success for unsigned development artifacts does not establish origin or make them retention candidates. Signature-only success does not authenticate the profile, timestamp or source estate; checksum and archive enrichment require the authenticated manifest and matching inventory digests. An otherwise successful signed observation whose digests disagree with the row marks it conflicting and records a failed observation. A verification that cannot establish digests records a failure; reconciliation determines whether the files are conflicting. Older binaries refuse the new schema.

## A05 restore ownership contract

Restore execution takes the store activity claim, an exclusive target lock, and a shared artifact-use lock in that order before opening the artifact or performing cluster mutations. Lock acquisition is nonblocking except for the existing bounded activity wait; refusal leaves the target untouched. Target identity uses the local PostgreSQL port and exact target database name in a domain-separated digest; the supported source hosts are loopback aliases, which intentionally share that lock. Locks coordinate processes using the same storage root, not unrelated stores or external database clients. Artifact use is shared across restores; a future deletion must take the same artifact lock exclusively. A restore job remains running until all restore and artifact-update work finishes; an error attempts to record failure and leaves any partial target or roles for operator repair. If the failure cannot be recorded, the job remains running for later recovery. When the process and any inheriting children exit, a later exclusive maintenance pass may record interruption. Job output identifies the operation and safe target fingerprint, never the target name.

Native subprocesses inherit restore claims: if the CLI is killed but a PostgreSQL subprocess remains alive, the claims stay held until that child exits. A later maintenance pass probes the target claim before marking the job interrupted. If a restore succeeds but its completion event cannot be recorded, the command reports that problem and leaves the job running for later interruption recovery, rather than claiming the restore failed. Schema v5 adds operation and target associations without rewriting or guessing older jobs. The pre-existing non-null profile column uses an internal placeholder for restore jobs; the public job report renders it as unknown. Older binaries refuse schema v5. No target database or role is automatically dropped or retried.

Restore execution requires an existing, bound inventory. If it is missing, explicitly rebuild it with the expected source fingerprint before running a restore; the command does not invent an estate from the target connection. For a restore into a different PostgreSQL instance, the job's source fingerprint comes from the inventory binding, and the target fingerprint describes the destination separately. Signature verification and inspection without an inventory remain available subject to their existing requirements.

## A06 recovery and integrity drill

Run `bash tests/m5a_docker_smoke.sh` as a non-root user with Docker access, Python 3, Cargo's locked offline dependencies, and Linux `strace` supporting syscall delay injection. It uses the existing PostgreSQL 16/17/18 images, matching container-native client tools, temporary keys/stores, and isolated synthetic databases. Containers have no network; the temporary directory is their only host mount. Cleanup removes the drill's containers and temporary files.

The drill interrupts a real streaming dump after archive bytes have been emitted and interrupts a real restore paused inside a fixture-only DDL trigger. It asserts duplicate refusal, unrelated-read safety, abandoned-stage recovery, same-scope restart, surviving native-child claims, interrupted job recovery, retained partial targets, and a subsequent restore checked against the SQL fixture. A registration trigger injects failure after publication; the complete artifact survives and can be explicitly adopted and verified.

Keyless scenes cover all three artifact shapes, malformed headers, foreign-estate refusal, stale plans, missing-index rebuild, unknown facts and lost history. Rebuild crash checkpoints cover exclusive stage creation, staged-file sync, old-index hard link, directory sync after that link, replacement rename, and final directory sync. A baseline trace discovers syscall ordinals for the current build; each scene delays the selected successful syscall and kills the process before userspace continues. The active index and any preserved old index are checked through actual CLI startup, followed by another explicit rebuild. Abandoned staging databases and plans may remain after a real crash; they are not automatically promoted.

Migration scenes use the actual v1/v2 migration SQL with populated artifact facts, upgrade through CLI backup startup, and refuse a newer schema without changing its bytes. Corruption zeroes 512 bytes of a populated index page while table counts still work; `inventory check` must report structural damage and explicit rebuild must preserve the damaged original. A current single-file inventory copy is read in a non-writable directory with absent keys, clients and artifacts.

These are process-crash tests on the host filesystem, not power-loss or faulty-storage simulations. A07's broader metadata/audit checks and A08's full regression and acceptance gates remain separate.
