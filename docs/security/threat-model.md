# Threat model

Status: M0 baseline, 2026-09-26; revised 2026-09-27 for the hybrid post-quantum decision; revised 2026-10-01 for the M4b origin signature and the artifact v1 freeze, against `tests/m4b_docker_smoke.sh` and the signing half of `tests/m4a_key_drill.sh` on PostgreSQL 16, 17 and 18; revised again 2026-10-01 when [ADR 0003](../architecture/adr-0003-backup-inventory-jobs-retention.md) scoped M5 — no row closes today, and T03 is recorded as staying open past the ledger M5 accepts. Review again when M5a's inventory lands, at M7 API, and at each release. Scope is the Rust backup service, PostgreSQL logical dumps, local artifact store, keys, catalog, CLI, and future API. A signed/encrypted backup can still contain malicious PostgreSQL SQL. This model does not assume the source server, backup host, and storage are equally trusted.

## Assets and trust boundaries

Assets: source database data and credentials; backup payload and private metadata; the hybrid age decryption identity, of which both halves (X25519 and ML-KEM) must be retained, because losing either one makes the artifact unreadable while an attacker holding only one learns nothing; the hybrid Ed25519 + ML-DSA-65 signing key, whose loss costs only the ability to publish; PostgreSQL restore target; catalog/audit history; availability of at least one restorable copy. Boundaries: source PostgreSQL -> `pg_dump` process -> Rust runner -> staging directory -> artifact store -> `pg_restore` -> target. Local operator/CLI and future API actors enter at separate authorization boundaries. Public artifact headers and remote/local storage are untrusted inputs. The independently installed trusted verifying key is not read from an artifact. M4b adds a boundary that did not exist in M4a: a **writer** host, which holds the identity and the signing seed, and a **reader** host, which by configuration holds the identity and the verifying key and no signing secret — so the two no longer share an asset set, and a compromised reader cannot produce a v1 artifact that any reader trusts. It is not powerless though: a reader that holds the recipient can still seal an *unsigned* artifact of the M4a shape, and ADR 0002's accepted choice 4 keeps that readable shape accepted rather than orphaning what M4a wrote. That is why `backup create` still requires `--confirm-synthetic` in every configuration, including a fully signed one: the signed format is the condition for real data, not a switch that lifts the guard. **Observed on 2026-10-01, outside the matrix:** a store holding both a v1 artifact and an unsigned M4a artifact was read through both configurations. The signed configuration lists the unsigned entry and names it as having no record without keys, then refuses every read of it with a bare OS stat error, because the signed reader looks for the `public.json` that shape does not write; the `[encryption]`-only configuration refuses a v1 artifact with a sentence naming the mismatch, for `backup list` as well as for verification. Mixed-store reading is therefore demonstrated behavior with an unclear message rather than an unproven path, and choosing which configuration opens which artifact stays M5 catalog work.

## Threat register

| ID | Attacker; asset | Attack and impact | Required mitigation; residual risk | Test/gate |
| --- | --- | --- | --- | --- |
| T01 | Backup-file thief; data | Copies archive now and decrypts it later, including possible database-held credentials | Encrypt payload/private manifest with the hybrid `mlkem768x25519-v0` recipient (ML-KEM-768 first, then X25519) inside age's authenticated stream; private identity outside store. Both a classical break and a lattice break must land to read a long-lived artifact. A compromised running host can still expose plaintext. | E05/E06, M4a |
| T02 | Storage editor; integrity/origin | Replaces both age files with attacker-created ciphertext for public recipient, or claims a weaker suite | Detached hybrid Ed25519 + ML-DSA-65 signature over ID and both ciphertext hashes, trusted verifier outside artifact. A ciphertext pair the signer did not authorize fails at `--level signature`, before any decryption or `pg_restore`, and a foreign signing key fails the same way. **Residual, accepted:** the signature does not cover the suite or ID strings in `public.json`, so a downgrade claim there survives signature level and is refused only when the authenticated manifest is compared against the header — reachable at `--level checksum`, `--level archive` and `restore plan`, so no restore path acts on the header's word, but a reader that trusts a suite string *because the signature verified* is misreading it. Signing-key compromise still permits forgery. | m4b matrix 6.1/6.4/6.5/6.6/6.11, `signed_write_path.rs`, drill step 9 |
| T03 | Storage editor; recoverability | Deletes or replays an older valid signed artifact | Independent inventory, alerting, protected/off-host copies and later immutable store. Local v1 alone cannot prevent host-loss/deletion/rollback. The freeze does not change this row: `signature.hybrid` carries no generation or sequence, so an older artifact from the *same* generation verifies perfectly. **Scoped 2026-10-01 (ADR 0003 choice 6B):** M5 adds a local high-water-mark ledger to the inventory, which sits inside the store's own failure domain, so it notices accidents and lazy edits and nothing more — **this row stays open** until the chained, signed, off-host inventory that ADR 0003 defers exists. | E10, M5+ — **untested, not claimed** |
| T04 | Local user; filesystem | Path traversal, malicious filename, symlink race, unauthorized deletion | Opaque validated ID, directory ownership/mode, no-follow file operations, atomic stage/commit, least-privilege service account. | E09, M1/M4 |
| T05 | Malicious source admin; restore target | Puts executable SQL/functions in dump; target compromise | Treat archive as executable, trusted-source policy, inspect TOC/SQL if source untrusted, isolated target, restricted restore role. Signature authenticates signer, not SQL safety. | F04, M2 |
| T06 | Credential thief; source | Reads `.pgpass`/connection info; source data disclosure | Peer auth or dedicated 0600 password file, TLS verification remotely, least-privilege role, no argv/logged URL. | P01–P04, M1 |
| T07 | Malicious local/API actor; target | Requests destructive restore or deletion | RBAC, plan digest bound to target/actor/expiry, explicit confirmation, audit, rate/size limits, fresh-target default. | E04/E10, M2/M7 |
| T08 | Crafted identifier; runner | Shell injection or tool option injection | No shell; fixed absolute binary, argv array, explicit option separation, exact catalog resolution, restricted environment. | E09, M1 |
| T09 | Disk/process failure; artifact | Partial write appears complete | Stage, fsync, immutable publish, marker, signature, native exit check, quarantine and startup reconciliation. A reader refuses a directory with no `complete` before any crypto work, and refuses a split artifact that carries both a plaintext `manifest.json` and a `manifest.age` rather than guessing which is authoritative. **Residual:** that refusal surfaces as a bare `No such file or directory` from the stat, not as a sentence naming the marker, so an operator triaging a store reads errno, not policy. | m4b matrix 6.7, E01/E02, M1/M4 |
| T10 | Key loss; recovery | Valid backups become unreadable, or a generation can no longer publish | Separate offline recovery copy of the full hybrid identity including its ML-KEM half, plus the signing seed and the verifying file, one generation per key directory, restoration drill, no destructive key rotation. The two secrets fail differently and the drill proves both: identity loss makes artifacts inert, signing loss stops only publication and leaves every artifact verifiable and restorable on the public half alone, and verifying-key loss costs trust rather than data — re-installing it is sufficient because no byte moved while it was gone. Post-quantum key material is larger and newer tooling may not display it, so the recovery drill is tested on the actual file format. | drill steps 1–11, m4b matrix, E06 |
| T11 | Compromised backup host; source/keys | Exfiltrates live keys and data or signs fake backup | Dedicated user, filesystem sandbox, short key exposure, host hardening, independent monitoring. A **verify-only or DR host can now be configured so that it holds no signing secret at all** — omitting `signing_key_file` is what makes that a property of the configuration rather than of trust in its operator — but the backup host itself must hold both the identity and the signing seed while it runs, so host compromise on the writer remains severe: it can publish an artifact that every reader will trust. | Package security, M6 |
| T12 | Catalog loss; discoverability | Backup list disappears or stale state hides artifacts | Rebuild from signed artifacts with recovery identity; catalog backup and migration tests. `public.json` already makes discovery possible with no key material, which is what an M5 rebuild would scan. | M5 |
| T13 | Metadata observer; privacy | Learns DB names/sizes/times | Minimal public header and encrypted private manifest. Ciphertext sizes and artifact count remain visible. M4b closes the M4a gap in this row: the manifest is now inside `manifest.age` rather than a plaintext `manifest.json` beside the ciphertext, so scope, timings, versions and database identity are no longer readable by whoever can read the store. | M4 — closed for the manifest by M4b |
| T14 | Malicious extension/FDW/subscription; target | Restore contacts external service, loads extension, or leaks credentials | Preflight packages/privileges, `--no-subscriptions`, no auto-activation, document FDW dependencies, treat archive as sensitive. | F05/F11/F12, M2/M3 |
| T15 | Backup overload; source availability | Too many dumps, long locks, disk/CPU pressure | Per-source job limit, bounded workers, lock wait timeout, resource budget and alerts. | M5 |
| T16 | Tool/version mismatch; recoverability | Older client refuses source or restore SQL incompatible | Matching source-major client, same-major restore matrix, extension/locale preflight, repeated restore drills. | E03, M1/M2 |

PostgreSQL explicitly warns that restoring a dump can execute code selected by a source superuser. [`pg_dump`](https://www.postgresql.org/docs/18/app-pgdump.html). User mappings and subscription connection strings can include passwords, so `--no-subscriptions` does not make an archive nonsensitive. [User mappings](https://www.postgresql.org/docs/18/sql-createusermapping.html), [subscription catalog](https://www.postgresql.org/docs/18/catalog-pg-subscription.html). The age recipient is public; sender provenance requires the separate trusted signature described in [artifact v1](../backup-format/manifest-v1.md). The post-quantum halves are defense against a future break, not against a present one, and they add size and CPU cost that is measured rather than assumed; see the [hybrid rationale](post-quantum-hybrid.md). Two properties of the shipped signature are worth stating rather than leaving implied. It is **deterministic** — no entropy is consulted when signing — so the same artifact bytes always produce the same 3373 bytes, which makes a re-sign reproducible and an audit comparable; and it carries **no timestamp, nonce, or sequence number**, so it cannot by itself tell a newer artifact from an older one. That is T03's problem and it is unchanged by M4b. An ML-DSA signature is not unique for a given message (a different valid hint encoding verifies too), which is harmless only because nothing treats signature bytes as an identity: the artifact's identity is its UUID, `signature.hybrid` is accept/reject input alone, and `signer_id` derives from the verifying key rather than from a signature. The classical leg is checked with `verify_strict`, so a non-canonical encoding or a small-order `R` is refused rather than accepted by a lenient verifier.

## Security invariants

- No real-data artifact is published before M4a encryption **and** M4b origin signing are implemented and verified. Both landed, so this invariant is now a configuration statement: a store that carries `[encryption]` but no `[signing]` writes `m4a-development-age`, which is unsigned, and must not be pointed at real data.
- A new write never selects a classical-only recipient or signature suite, and a reader never accepts a suite outside its configured accepted list; neither infers the suite from key sizes. What "accepts" means is split, and stated here so it is not over-read: the header's suite strings are checked against the **readable** list at discovery, and the authenticated manifest's are the authoritative ones. A `signature.hybrid` is always the full 3373-byte hybrid — there is no code path that validates a 64-byte classical signature, so a header cannot be talked into a weaker check by naming a weaker suite.
- The signed tuple covers `backup_id` and the two ciphertext digests only. It does not cover `public.json`'s suite or ID fields, its sizes, or `globals.age`; globals is bound one step in, by the digest inside the signed manifest. A control that treats "the signature verified" as authentication of every field in the discovery record is wrong, and m4b case 6.11 pins the boundary.
- A published manifest records `verification_level: none`, and no reader raises it in place. `archive_toc_sha256` is computed from the staged archive *before* sealing, precisely so that archive level can compare against something the signer saw; a restore reports what it did to the artifact without writing into it. This is what keeps verification levels from becoming a claim an attacker with the identity can rewrite.
- `source_fingerprint` binds an artifact and a plan to one source, checked at `restore plan` **and** at `restore run`, so a plan cannot be replayed against a different database than the one it was built for. The fingerprint is a digest rather than `host:port/database`, so binding does not disclose where the source is.
- A published artifact carries exactly one recipient stanza, the hybrid one. The writer refuses a configuration that would also wrap the same file key to a classical-only recipient, because age will accept such a mixed header and either identity would then decrypt alone, cancelling T01's mitigation. Age's own random `*-grease` stanza, which it appends to every header it writes, is not a recipient and is the only other stanza the reader tolerates.
- Payload and globals plaintext never enters `artifacts/` or `staging/`: `pg_dump` writes to a pipe that goes straight into the age stream, and decryption writes only to a mode-0700 `scratch/` directory that the operation which created it removes when it ends and that the store purges at startup. A host compromised during a restore can still read that transient copy, which is why T01's mitigation is stated as protection of the stored artifact rather than of a running host.
- No service password or signing/decryption private key is stored in the repository, profile, public header, private manifest, logs, or backup store, and none is printed: the age identity's 64-hex seed and the signing file's 128-hex seed appear in no `key status`, no `--output json`, and no error text, which the drill and the m4b matrix both grep for rather than assume.
- Verification labels are distinct: ciphertext/signed-artifact integrity, archive readability, and actual isolated restore success. `--level signature` proves origin while decrypting nothing and invoking no PostgreSQL tool; `--level archive` proves the archive still parses to the table of contents the manifest recorded; only `restore run` proves a restore.
- A verified signature does not authorize restore; the actor and target still need authorization and an explicit plan.
- Destructive restore and deletion are never inferred from a profile or retried automatically.
- No guarantee of survival of backup-host loss exists until copies reside on independent failure domains.

## Review triggers

Revisit attacker capabilities and mitigations whenever a new storage provider, recipient/key provider, algorithm suite or accepted-suite list, API/UI, global-object export, physical/WAL backup mode, or multi-tenant model is added. Record owner, review date, changed trust boundary, tests, and accepted residual risk in the corresponding ADR/release note.
